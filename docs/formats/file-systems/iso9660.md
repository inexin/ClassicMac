# ISO 9660 and High Sierra

ISO 9660 (ECMA-119) and its predecessor High Sierra are the CD-ROM file systems of most discs not mastered for the
Mac alone. Mac OS 9 reads them through two Foreign File Access plug-ins, ISO 9660 File Access and High Sierra File
Access 5.3, built from one source. The on-disc layout is the standard's; everything the Mac adds or decides for itself
comes from those plug-ins: which descriptor it uses, how identifiers become Mac names, where type and creator come
from (Apple's `AA` and `BA` system-use entries), which record is the resource fork, how dates and damaged directories
are handled. ClassicMac lists the same files, with the same names, types, creators, Finder flags, icon positions,
dates and forks, as a Mac running Mac OS 9.0 shows for the same disc.

| | |
| --- | --- |
| Identified by | `CD001` (or `CD-I `) at byte 1 of a descriptor from sector 16 (byte `$8000`); High Sierra's `CDROM` at byte 9 |
| ClassicMac | Reads: `ClassicMac.Files.Iso` (`IsoReader`) |
| Verified against | A test disc read in SheepShaver, Mac OS 9.0, with the Mac's own listing of every entry |
| Sources | ECMA-119; the High Sierra proposal; ECMA-130, CD-ROM XA and CD-i; Apple's ISO 9660 extensions; ISO 9660 File Access and High Sierra File Access 5.3, Apple CD/DVD Driver 1.3.1 (disassembly) |

## 1. Layout

### 1.1 Conventions

- **Both-endian fields.** ISO 9660 and High Sierra store most numbers twice: a little-endian copy followed by a
  big-endian copy of the same value (`u32 both` is 8 bytes, `u16 both` is 4) [Doc: ECMA-119]. The tables give the
  offset of the whole pair and note which half the Mac reads. The Mac, a big-endian machine, reads the **big-endian
  half** of every pair, and the big-endian (type M) path table; the one little-endian value it reads is the path table
  size, only to compare it with the big-endian one (§2.2) [Code].
- A **sector** here is **2048 bytes**, a CD-ROM mode 1 user-data block. A **logical block** is the volume's own block
  size (§1.3), 512, 1024 or 2048 bytes; extents and lengths in blocks use it. A **raw sector** is 2352 or 2336 bytes
  ([cd-images.md](../disk-images/cd-images.md)).
- Identifier text on the disc is raw bytes; the Mac shows those bytes as **Mac OS Roman**, untranslated.
- [Code] without a name means ISO 9660 File Access (or High Sierra File Access) 5.3 from Mac OS 9.0; [Code: CD
  driver] means Apple CD/DVD Driver 1.3.1. [Verified] means the test disc was read in SheepShaver, Mac OS 9.0 (the
  image attached as a disk, since SheepShaver serves CDs through its own driver) and the Mac's listing matched.

### 1.2 Volume descriptors

The volume descriptors start at **sector 16** (byte `$8000`), one per 2048-byte sector, and end with a terminator
[Doc: ECMA-119]. Sectors 0–15 are the system area, which the ISO reader ignores [Doc: ECMA-119].

| Type | Name | Mac OS 9 |
| --- | --- | --- |
| 0 | Boot record (El Torito) | Ignored [Code] |
| 1 | Primary volume descriptor (§1.3); High Sierra's standard file structure volume descriptor (§1.4) | Used |
| 2 | Supplementary (Joliet when its escape sequences say UCS-2) | Ignored [Code] |
| 3 | Volume partition | Ignored [Code] |
| 255 | Terminator: ISO's at byte 0 with `CD001`; High Sierra's at byte 8 with `CDROM` [Doc] | Ends the search [Code] |

### 1.5 The path table

The path table lists every directory with its extent [Doc]. The Mac reads only its first entry (§2.4).

ISO 9660 path table record [Doc: ECMA-119]:

| Offset | Size | Field | Notes |
| --- | --- | --- | --- |
| +$0 | 1 | identifier length | Length of the directory identifier |
| +$1 | 1 | extended attribute record length | In logical blocks |
| +$2 | 4 | extent location | In logical blocks; big-endian in a type M table (**used**) |
| +$6 | 2 | parent directory number | |
| +$8 | n | directory identifier | The root's is one zero byte; padded to even length |

High Sierra path table record [Doc: High Sierra proposal]:

| Offset | Size | Field | Notes |
| --- | --- | --- | --- |
| +$0 | 4 | extent location | In logical blocks; big-endian in a type M table (**used**) |
| +$4 | 1 | extended attribute record length | |
| +$5 | 1 | identifier length | |
| +$6 | 2 | parent directory number | |
| +$8 | n | directory identifier | Padded to even length |

The path table's byte offset is location × logical block size; the root's is extent × logical block size.

### 1.6 Directory records

A directory is a run of variable-length records packed into sectors. A record never crosses a 2048-byte sector
boundary; the rest of a sector after its last record is zero [Doc].

ISO 9660 directory record [Doc: ECMA-119]:

| Offset | Size | Field | Notes |
| --- | --- | --- | --- |
| +$00 | 1 | record length | In bytes, even; 0 = no record here |
| +$01 | 1 | extended attribute record length | In logical blocks |
| +$02 | 8 | extent location | u32 both, in logical blocks; big-endian half at +$06 (**used**) |
| +$0A | 8 | data length | u32 both, in bytes; big-endian half at +$0E (**used**) |
| +$12 | 7 | recording date and time | §1.9 |
| +$19 | 1 | file flags | Below |
| +$1A | 1 | file unit size | In logical blocks; 0 = not interleaved |
| +$1B | 1 | interleave gap size | In logical blocks |
| +$1C | 4 | volume sequence number | u16 both |
| +$20 | 1 | identifier length | n |
| +$21 | n | file identifier | |
| +$21 + n | 0 or 1 | pad | Present when n is even |
| … | to the end | system use | §1.8 |

High Sierra directory record [Doc: High Sierra proposal]:

| Offset | Size | Field | Notes |
| --- | --- | --- | --- |
| +$00 | 1 | record length | |
| +$01 | 1 | extended attribute record length | |
| +$02 | 8 | extent location | u32 both |
| +$0A | 8 | data length | u32 both |
| +$12 | 6 | recording date and time | Year − 1900, month, day, hour, minute, second; no time zone |
| +$18 | 1 | file flags | |
| +$19 | 1 | reserved | |
| +$1A | 1 | interleave size | |
| +$1B | 1 | interleave skip factor | |
| +$1C | 4 | volume sequence number | u16 both |
| +$20 | 1 | identifier length | n |
| +$21 | n | file identifier | Then a pad byte when n is even, then system use |

ISO 9660 file identifiers have the form `NAME.EXT;1`, the number after `;` being the file version; directory
identifiers have no version [Doc]. The first two records of a directory are `.` (the directory itself) and `..` (its
parent), with one-byte identifiers 0 and 1 [Doc].

File flags [Doc]:

| Bit | Mask | Meaning | Mac OS 9 |
| --- | --- | --- | --- |
| 0 | `$01` | Existence: hidden from the user | Invisible (§2.9) [Code] [Verified] |
| 1 | `$02` | Directory | Folder; not on CD-i discs (§1.7) [Code] |
| 2 | `$04` | Associated file | Resource fork (§2.8) [Code] [Verified] |
| 3 | `$08` | Record format in the extended attributes | Ignored [Code] |
| 4 | `$10` | Permissions in the extended attributes | Ignored [Code] |
| 5–6 | `$60` | Reserved | Ignored |
| 7 | `$80` | Multi-extent: not the file's last extent | Ignored: each extent is its own entry (§2.8) [Verified] |

### 1.7 CD-i directories

A disc whose descriptor says `CD-I ` keeps a directory's "is a folder" bit in its system-use field, not in the flags:
the system use starts with a 4-byte owner ID and a 2-byte attributes word, and bit 15 of the attributes (byte 4 of the
system use, mask `$80`) marks a directory [Doc: CD-i]. The hidden and associated bits still come from the flags.

### 1.8 Apple's system-use entries

The system-use field starts at record offset `$21 + n`, plus one pad byte when n (the identifier length) is even, and
runs to the record length [Doc: ECMA-119]. Two forms of Apple's extension exist.

`BA`, the old form, only at the start of the system-use field [Code]:

| Offset | Size | Field | Notes |
| --- | --- | --- | --- |
| +$0 | 2 | signature | `BA` |
| +$2 | 1 | kind | §2.9 |
| +$3 | 4 | type | `OSType` |
| +$7 | 4 | creator | `OSType` |
| +$B | 2 | Finder flags | Used by kind 6 only |

What the kinds mean is not in the code. Likely: 1 is ProDOS (ignored here), 2 and 3 HFS type and creator without and
with a bundle, 4 and 5 the same in a form that also carries an icon (ignored), and 6 HFS with explicit Finder flags.

`AA`, Apple's extension [Doc: Apple ISO 9660 extensions]:

| Offset | Size | Field | Notes |
| --- | --- | --- | --- |
| +$0 | 2 | signature | `AA` |
| +$2 | 1 | length | 14 for the HFS form |
| +$3 | 1 | system-use ID | 1 = ProDOS, 2 = HFS |
| +$4 | 4 | type | `OSType` (HFS form) |
| +$8 | 4 | creator | `OSType` (HFS form) |
| +$C | 2 | Finder flags | HFS form |

### 1.9 Dates

ISO 9660 dates in directory records are 7 bytes [Doc: ECMA-119]; High Sierra has the first six only [Doc: High Sierra
proposal]:

| Offset | Size | Field | Notes |
| --- | --- | --- | --- |
| +$0 | 1 | year | Year − 1900 |
| +$1 | 1 | month | 1–12 |
| +$2 | 1 | day | 1–31 |
| +$3 | 1 | hour | 0–23 |
| +$4 | 1 | minute | 0–59 |
| +$5 | 1 | second | 0–59 |
| +$6 | 1 | GMT offset | i8, in 15-minute steps; ISO only |

The descriptor's volume dates are 17-byte text dates [Doc: ECMA-119].

## 2. Reading

### 2.1 From image to volume

A CD image reaches the volume readers as a run of 2048-byte blocks, the same thing a CD drive hands the Mac:

| Input | What is done | Then |
| --- | --- | --- |
| Cooked image (`.iso`, `.toast`, `.cdr`, `.img`): 2048-byte blocks | Nothing | Volume readers |
| Raw image (`.bin`): 2352- or 2336-byte sectors | User data cut out of each sector ([cd-images.md](../disk-images/cd-images.md)) | Volume readers |
| Cue sheet (`.cue`) with its `.bin` beside it | Data tracks placed at their sectors, cut as above, last session found ([cd-images.md](../disk-images/cd-images.md)) | Volume readers |

The Mac's CD driver never parses sectors: it asks the drive for 2048-byte blocks, and the drive strips sync, header,
subheader and error-correction bytes [Code: CD driver]. So the 2048-byte blocks are all a Mac file system ever sees,
and raw sector bytes cannot change what the Mac shows. File extensions play no part: every container is recognised by
content. The volume readers are then tried in the Mac's mount order (§2.11).

### 2.2 Finding the descriptor

1. Find an **anchor**: the sector 16 sectors after the start of the last session
   ([cd-images.md](../disk-images/cd-images.md)), then sector 16 itself. The anchor passes when its identifier is
   `CD001` or `CD-I ` and its version is 1; its type byte is not checked. Nothing else is tried: with no anchor the disc
   is not an ISO volume (−58) [Code].
2. From the anchor, examine each sector in turn [Code]:

   | Test | Meaning |
   | --- | --- |
   | byte 0 = 255 and bytes 1–5 = `CD001` | ISO terminator: stop, no volume |
   | byte 8 = 255 and bytes 9–13 = `CDROM` | High Sierra terminator: stop, no volume |
   | byte 0 = 1, byte 6 = 1, bytes 1–5 = `CD001` | ISO 9660 primary volume descriptor |
   | byte 0 = 1, byte 6 = 1, bytes 1–5 = `CD-I ` | A CD-i disc's primary descriptor, read as ISO 9660 with the CD-i rules (§1.7) |
   | byte 8 = 1, byte 14 = 1, bytes 9–13 = `CDROM` | High Sierra standard file structure volume descriptor |
   | anything else (boot record, supplementary, partition) | Skipped |

   There is **no fixed limit** on the number of sectors examined: the scan runs until a primary descriptor, a
   terminator (with no primary descriptor: −60) or a read error (−58) [Code].
3. Only the **primary** descriptor is used. A supplementary descriptor, and so Joliet, is never used; the plug-in has
   no Unicode name code at all [Code]. Rock Ridge is not read either (§2.9).
4. The volume is **rejected** when the file structure version (+$371) is neither 0 nor 1, or, on an ISO (not CD-i)
   disc, the little- and big-endian path table sizes differ [Code]. High Sierra has no file structure version check
   and no path table size comparison [Code].

### 2.3 Discs the ISO plug-in declines

A disc whose ISO descriptor passes §2.2 can still be declined by the ISO plug-in [Code]:

- **Photo CD.** The plug-in answers −58, leaving the disc to Kodak's Photo CD Access, when all of these hold: the
  system identifier (+$008, 17 bytes) is `CD-RTOS CD-BRIDGE`; the descriptor holds `CD-XA001` at byte `$400`; bytes
  `$40`–`$5F` of logical sector 0 read `PPPPHHHHOOOOTTTTOOOO____CCCCDDDD` ("PHOTO_CD" with each character four times);
  and Gestalt `'kpcd'` exists, that is, Photo CD Access is installed. Without it, a Photo CD mounts as an ordinary ISO
  volume.
- **UDF.** When Gestalt `'kudf'` exists, the plug-in examines up to 10 sectors after the primary descriptor (the count
  stops falling once `BEA01` is seen; the search ends at `TEA01` or a read error) and answers −58 if it finds `NSR02`,
  so UDF takes the disc.

### 2.4 The root directory

The root directory is **the first entry of the big-endian (type M) path table** [Code]. The root directory record
inside the descriptor is not used, and nothing else in the path table is read: every other directory is found through
directory records [Code].

### 2.5 Listing a directory

A directory is reached through a record for it; for the root, the first record at the path table's extent, which is
the root's own `.` record. Its listing [Code]:

1. `start` = (the record's extent + its extended attribute length) × logical block size.
2. The first record at `start` is `.`; its data length gives the directory's size, so `end` = `start` + that length.
3. The second record is `..`.
4. Entries are read from after `..` to `end` (§2.6).

`.` and `..` are recognised by position, not by their identifiers [Code].

Each entry is one file or one folder. A folder is a record with the directory bit (§1.6, §1.7). A file is one record,
or two records paired as data and resource fork (§2.8). Entries are numbered from 1 in listing order within their
directory, folders included; the number places the Finder icon (§2.9) [Code] [Verified]. The Mac never walks the tree:
a folder is read only when opened, with no loop check, so a folder that points at itself or an ancestor shows the
target's contents again, nested without end, with the parent ID taken from the target's `..` record [Code].

### 2.6 Valid records

A record is **valid** when all of these hold [Code] [Verified]:

| Test | Failing it means |
| --- | --- |
| record length ≠ 0 | The unused tail of a sector |
| extent (big-endian, read as signed) > 0 | A record with extent 0, which some discs use for an empty file |
| 1 ≤ identifier length ≤ 37 | A damaged record, or a long name from a non-conforming mastering program |
| High Sierra only: year byte ≤ 140 (year ≤ 2040) | — |

An invalid record is handled like the zero tail of a sector [Code] [Verified]:

1. Move to the next 2048-byte sector boundary (of the image, whatever the logical block size). If the position is
   already on a boundary, it stays there.
2. If that is at or past `end`, the listing ends.
3. If the record there is invalid too, the listing ends.
4. Otherwise it is the next entry.

So an invalid record in the middle of a sector **hides the rest of that sector**, and an invalid record at the start
of a sector **ends the whole directory** [Verified]. A 38-byte identifier or an empty file stored with extent 0
therefore makes files disappear from the Mac's listing.

The plug-ins copy a fixed amount of each record into a buffer: **268 (`$10C`) bytes** for ISO 9660, **82 (`$52`)**
for High Sierra [Code]. Bytes past the end of the image read as zeros. An ISO record is at most 255 bytes, so the
buffer holds all of it and some of what follows; a system-use entry that starts inside the record is read in full even
when it runs past the record's length [Code]. A High Sierra record is seen only as far as byte 81; system-use bytes
beyond it read as zeros [Code].

### 2.7 Names

The Mac converts an identifier to a name in this order [Code] [Verified]:

1. **Cut to 31 bytes**, the longest Mac file name, before anything else, so a long name loses its version or part of it
   first.
2. **Trim trailing spaces.**
3. **Strip the version:** if the name ends in `;` followed by nothing but digits (possibly none), remove the `;` and the
   digits.
4. **Drop a final `.`**, but only when the name is **9 bytes or shorter** at this point.

Nothing else changes [Code] [Verified]: the bytes are shown as Mac OS Roman, with no character set conversion; case is
kept (`mixed.Case;1` stays `mixed.Case`); `:` is not filtered, though it is the Mac's path separator; there is no 8.3
check and no mapping of `_` or other characters. High Sierra names follow the same rules [Code].

Examples [Verified]:

| Identifier | Bytes | Mac name |
| --- | --- | --- |
| `README.TXT;1` | 12 | `README.TXT` |
| `NOEXT.;1` | 8 | `NOEXT` |
| `LONGNAME12.;1` | 13 | `LONGNAME12.` (the dot is kept: 11 bytes after the version goes) |
| a 30-byte name + `;1` | 32 | The 30-byte name (the cut leaves `…;`, and the empty version goes) |
| a 33-byte name + `;1` | 35 | Its first 31 bytes |

Two records that convert to the same name are both listed [Code]. The Mac looks names up without regard to case and
finds the first [Code]. Multi-extent files and a data fork before its resource fork (§2.8) both produce such
duplicates [Verified].

### 2.8 Forks

An **associated file** (flag bit 2) holds the **resource fork** of the file with the same name [Code] [Verified]. The
two records must be **adjacent**, in this order:

| Format | First record | Second record |
| --- | --- | --- |
| ISO 9660 | The associated one (resource fork) | The file (data fork) |
| High Sierra | The file (data fork) | The associated one (resource fork) |

Pairing rules [Code] [Verified]:

- ISO: an associated record takes the **immediately following** record as its data fork when that record is valid, is
  not associated itself, and has the same converted name (§2.7). The pair is one entry. A second associated record
  after an associated one starts an entry of its own [Code].
- High Sierra: a record takes the immediately following record as its resource fork when that record is valid,
  associated, and has the same converted name.
- An associated record with no partner is a file with an **empty data fork** and that resource fork [Verified].
- Records in the wrong order for the format are **two entries with the same name**, one with only a data fork and one
  with only a resource fork [Verified].
- "The same name" is decided by `_RelString`, **case-insensitive and diacritical-sensitive**, on the converted names
  (at most 31 bytes, `;n` stripped) [Code]: `readme.txt` pairs with `README.TXT`, `CAFE` does not pair with `CAFÉ`,
  `A;1` pairs with `A;2`, and two names that differ only after byte 31 pair. This is the order and case folding the
  File Manager uses for HFS names, quirks included (`á` and `Á` differ, `$CA` equals a space)
  ([hfs.md §1.11](hfs.md#111-key-order)).

A fork's bytes start at (extent + extended attribute record length) × logical block size and run for the data length
[Doc] [Verified]. The extended attribute record's contents (owner, permissions, record format, dates) are ignored; only
its length moves the data [Verified].

An **interleaved** fork (file unit size ≠ 0) is stored as units of `unit` logical blocks separated by gaps of `gap`
logical blocks, starting with a unit [Doc]; the Mac reads it [Verified]:

```
offset = (extent + xar) × blockSize
repeat until length bytes are read:
    read min(unit × blockSize, remaining) bytes at offset
    offset += (unit + gap) × blockSize
```

ECMA-119 lets a file span several records with the same identifier, all but the last having flag bit 7 [Doc]. The Mac
does **not** join them: each extent is listed as a separate file of the same name [Verified].

The volume is read-only and locked; writes fail with `wPrErr` (−44) [Code].

### 2.9 Finder information

A file with no Apple extension is type `'TEXT'`, creator `'hscd'`, Finder flags `$0100` (hasBeenInited) [Code]
[Verified]. There is **no mapping from name extensions** to types [Code]: `.GIF`, `.SIT` and `.JPG` files are all
`'TEXT'`/`'hscd'` on the Mac.

For one record [Code]:

1. The system-use field is looked at only when `$21 + n` is less than the record length. Folders get no system-use
   processing.
2. If the field **starts** with `BA` (§1.8), its kind decides:

   | Kind | Type and creator | Finder flags |
   | --- | --- | --- |
   | 2 or 4 | From the entry | OR `$0100` |
   | 3 or 5 | From the entry | OR `$2100` (hasBundle, hasBeenInited) |
   | 6 | From the entry | OR ((stored flags AND `$B020`) OR `$0100`) |
   | anything else | `'TEXT'`/`'hscd'` | OR `$0100`; no `AA` search follows |

   Kinds 3 and 6 were checked on the test disc [Verified]. The XA skip of step 3 does not apply to `BA` [Code].
3. Otherwise scan for `AA` entries:
   1. `p` = the start of the system-use field; on an XA disc (§1.3), `p` += 14, skipping the XA system-use entry.
   2. While `p` + 14 fits in the record buffer (§2.6) and `p` is inside the record: if bytes `p`…`p+1` are `AA` and
      byte `p+3` is 2, this is the entry; stop. Else if the length byte at `p+2` is below 4, stop with no entry. Else
      `p` += the length byte.
   3. An `AA` entry of ID 2 gives the type, the creator, and Finder flags **set** (not ORed) to (stored flags AND
      `$B020`) OR `$0100` [Code] [Verified]. The ProDOS form (ID 1) is skipped [Verified].
   4. No entry: the defaults above.

The `AA` mask keeps only isAlias (`$8000`), hasBundle (`$2000`), nameLocked (`$1000`) and bit 5 (`$0020`) [Code]. It
removes, among others, **isInvisible** (`$4000`), **isStationery** (`$0800`) and **hasCustomIcon** (`$0400`), so an `AA`
entry can never make a file invisible, stationery or custom-iconned [Code] [Verified]: stored flags `$6500` read as
`$2100`. SUSP conventions are not honoured: no `SP` entry skip, no `CE` continuation areas [Code]; an `AA` entry in a
continuation area is never found.

For a file, starting from type `'TEXT'`, creator `'hscd'` and flags 0 [Code]:

1. For each record present, data first, then resource: take its type and creator as above (replacing what was there),
   apply its flag rule, and if the record's hidden flag (bit 0) is set, OR in isInvisible (`$4000`).
2. So the **associated (resource) record wins**: if it has no extension, the file is `'TEXT'`/`'hscd'` even when the
   data record has an `AA` entry [Code] [Verified]. Flags left by the data record survive when the resource record's
   rule ORs (default or `BA`) and are replaced when it has an `AA` entry; this follows from applying the rules in order
   [Code] and was not checked on the test disc.

The hidden flag is the only way a file becomes invisible on the Mac [Code] [Verified]. It hides folders too [Code].

**Icon positions.** Files listed by index, as the Finder lists a folder, get an icon position on a six-column grid of
64-pixel cells, in entry order (§2.5) [Code] [Verified]:

```
v = ((i − 1) div 6) × 64
h = ((i − 1) mod 6) × 64
```

with `i` the entry number from 1. The same formula with index 0 is used when a file is looked up by name, giving h =
−64, v = 0 [Code] [Verified]. The extended Finder information is all zero [Code].

### 2.10 Dates

The Mac's conversion of a record date (§1.9) [Code] [Verified]:

1. The date is taken as **local wall-clock time**; the **GMT offset is ignored** (12:00 at +9 hours and at −5 hours
   both read as 12:00) [Verified].
2. ISO: a year of **2040 or later** reads as **6 February 2040, 00:00:00**.
3. A year before 1904 reads as **1904**, month, day and time kept.
4. A month outside 1–12 reads as 1; a day outside 1–31 reads as 1.
5. Hours, minutes and seconds are not checked. The fields go to `Date2Secs`, plain arithmetic with no range checks, so
   a value past its range carries into the next unit: 31 February reads as 3 March (2 March in a leap year), and
   25:61:61 as 02:02:01 the next day. Its leap-year rule is "year divisible by 4", right for 1904–2040 [Code].

High Sierra: a record with a year byte over 140 is invalid (§2.6) [Code]. A file's creation, modification and backup
dates are all the date of its **associated (resource) record** when it has one, else of its data record [Code]
[Verified].

### 2.11 Hybrid discs

A **hybrid** disc carries an HFS volume and an ISO 9660 volume over the same data: typically an Apple partition map in
the system area, an HFS partition, and an ISO descriptor at sector 16. On the Mac [Code: CD driver] [Code]:

1. The CD driver looks at block 0: if it holds a driver descriptor (`ER`) or zeros, it scans for partition entries
   (`PM`) at a 512-byte stride, then at a 2048-byte stride. Each `Apple_HFS` partition becomes a drive of its own, and
   no whole-disc drive is made, so the ISO volume is never offered to the file systems
   ([partition-map.md §2.2](partition-map.md#22-which-partitions-are-volumes)).
2. Without a partition map, the whole disc is one drive. Mounting always tries HFS first (the master directory block
   at byte 1024); only when that fails do Foreign File Access and the ISO plug-in get the disc
   ([hfs.md §2.1](hfs.md#21-finding-the-volume)).

So **a hybrid disc mounts as HFS**, and its ISO side is never seen on a Mac; both cannot be mounted from one disc.

### 2.12 What else the Mac shows

- **Volume name**: the first 27 bytes of the volume identifier, trailing spaces trimmed, converted as in §2.7; an
  empty identifier gives `Untitled` [Code] [Verified].
- **Volume dates**: parsed from the descriptor's 17-byte text dates, GMT offset ignored [Code].
- **Folders**: Finder flags `$0100`, view `$0100`, scroll position (−8, −16); the hidden flag makes a folder invisible
  [Code].
- **File and folder IDs**: the byte offset of the entry's (first) directory record on the disc; the root's ID is 2
  [Code] [Verified].
- **A locked volume** (§2.8).

## 4. Variants

- **High Sierra** moves the descriptor (§1.4), the path table record (§1.5) and the directory record (§1.6), has 6-byte
  dates with no GMT offset and no 2040 clamp (§2.10), puts the data record before the resource record (§2.8), sees only
  82 bytes of each record (§2.6), and skips the file structure version and path table size checks (§2.2).
- **CD-i** discs (`CD-I `) keep the folder bit in the system use (§1.7) and skip the path table size comparison
  (§2.2).
- **CD-ROM XA** discs (`CD-XA001`) have an XA entry before Apple's `AA` entry (§2.9).
- **Holding Option at mount** skips steps 3 and 4 of §2.7 for the whole volume: names, the volume name included, keep
  `;1` and their final dot [Code]. The 31-byte cut, the space trim, case and character handling do not change. Lookups
  then need the raw name, and a resource fork pairs with its data fork only when the names, versions included, match,
  so `A;1` and `A;2` no longer pair [Code].

Where Mac OS 9 differs from ECMA-119:

| Standard | Mac OS 9 |
| --- | --- |
| Supplementary descriptors (Joliet) give long Unicode names | Ignored; only the primary descriptor (§2.2) [Code] |
| Rock Ridge (SUSP) entries give POSIX names and attributes | Ignored; `SP` and `CE` not honoured (§2.9) [Code] |
| The root is the descriptor's root directory record | The first entry of the big-endian path table (§2.4) [Code] |
| Both byte orders are equivalent | The big-endian half is read (§1.1) [Code] |
| Identifiers up to 207 bytes (level 3), versions 1–32767 | 31 bytes kept, cut before the version goes; over 37 bytes the record is invalid (§2.6, §2.7) [Code] [Verified] |
| A zero-length file may have any extent | A record with extent 0 is invalid and hides what follows (§2.6) [Verified] |
| A file may span several extents (flag bit 7) | Each extent is a separate file (§2.8) [Verified] |
| Associated files have no fixed meaning | The associated file is the resource fork (§2.8) [Code] [Verified] |
| Recording dates carry a GMT offset | The offset is ignored; dates are local (§2.10) [Verified] |
| Extended attribute records hold owner, permissions and dates | Only their length is used (§2.8) [Verified] |
| File flag bit 0 hides a file from the user | The only source of isInvisible (§2.9) [Code] [Verified] |
| Name characters are d-characters (A–Z, 0–9, `_`) | Any byte is shown as Mac OS Roman, case kept (§2.7) [Code] [Verified] |
| Descriptors from sector 16 | On a multisession disc, the last session's first (§2.2) [Code] |

## 5. ClassicMac

- **Reader order.** Partition map, HFS, MFS, DOS partition table, FAT, raw CD, cue sheet, ISO 9660
  ([hfs.md §5.1](hfs.md#51-recognising-a-volume)), so hybrid discs read as HFS, as on the Mac (§2.11). The partition
  map reader reads the map as the CD driver does; its remaining differences from the driver are in
  [partition-map.md §5](partition-map.md#5-classicmac). A raw image or a cue sheet comes out as one file (named after
  the image without its extension, or `CD`) whose data fork is the cooked disc, which the same readers then open.
- **Anchor.** The anchor is D + 16 only when the image's sessions are known (a cue sheet, or a raw image whose sector
  addresses jump; [cd-images.md](../disk-images/cd-images.md)); it passes with `CD001` or `CD-I ` at byte 1 and version
  1 at byte 6, or with High Sierra's `CDROM` at byte 9 and version 1 at byte 14, compared exactly. Once it passes, its
  scan decides. When the last session's root extent is at or after the session's start, block numbers are absolute;
  otherwise they count from the session's start. Otherwise the scan starts at sector 16 without testing it as an anchor.
- **Scan.** The standard identifiers in the scan, terminators' included, are compared without regard to case. The scan
  examines at most 64 sectors from its start, a limit the Mac does not have.
- **Root.** The volume is rejected when the logical block size is not a power of two from 512 to 2048, the path table
  or the root lies outside the image, or the root extent is 0.
- **Photo CD and UDF** discs are read as ISO 9660, as on a Mac without those extensions (§2.3).
- **Option** is never held: names are read as §2.7.
- **Listing.** Entries are read while the position is before `end`; a record that starts exactly at `end` is not read.
  Folders are read depth first in listing order, their files placed where the folder's record appears. A folder whose
  data (by byte offset) has already been read is skipped. Reading stops after `ContainerReadOptions.MaxVolumeEntries`
  entries (1,000,000 by default). Files come out with exactly the entries the Mac lists, invalid records hiding what
  they hide (§2.6).
- **Pairing.** Converted names are compared without regard to case as Mac OS Roman read into Unicode, with ordinal case
  folding, not with Apple's tables. The two agree on A–Z and on the accented letters `_RelString` folds; they differ
  where its tables do not fold (`á`/`Á` and `ÿ`/`Ÿ` pair in ClassicMac, not on the Mac) or equate other characters
  (`$CA` and a space pair on the Mac, not in ClassicMac). On ISO, a second associated record after an associated one is
  consumed by the pair but gives no fork, where the Mac starts an entry with it (§2.8).
- **Forks.** A fork that runs past the end of the image is cut at the image's end. Multi-extent files are listed as
  the Mac lists them.
- **Dates.** Computed as §2.10: a day past the end of its month rolls into the next month, and hours, minutes and
  seconds are added without range checks. Only a High Sierra date late in 2040 can pass the last Mac date (6 February
  2040, 06:28:15); ClassicMac reads it as that date.
- **Output.** Each file's name, folder path, type, creator, Finder flags, listed icon position, creation and
  modification dates (the same value) and both forks. Not reported: the volume name and dates, folder entries (only
  folder paths, so folder dates, flags and invisibility are lost), file and folder IDs, and the locked state (§2.12).
- Discs that fail the descriptor tests are not ISO 9660 volumes and are not reported; invalid directory records are not
  reported either, since the Mac treats them as the end of a sector or directory and lists what ClassicMac lists.

## 6. Diagnostics

| Code | Severity | When | ClassicMac does | The Mac does |
| --- | --- | --- | --- | --- |
| `iso.folder-loop` | Error | A folder record points at a directory already read (by byte offset) | Skips that folder | Has no loop check: the folder shows the target's contents again, nested without end (§2.5) [Code] |
| `iso.short` | Error | A fork runs past the end of the image | Cuts it at the end | A pressed disc cannot be short; no equivalent |
| `iso.too-many-entries` | Error | More than `MaxVolumeEntries` files and folders | Stops reading | No such limit |

## 7. Verification

- `tests/ClassicMac.Files.Tests/IsoTests.cs` builds discs with `IsoBuilder.cs`: names cut and stripped as §2.7; a name
  over 37 bytes or an empty file ending the listing; `AA` and `BA` entries giving type, creator and masked flags;
  associated files as resource forks whose Finder info wins; dates within the Mac's range; extended attributes and
  interleaving skipped; High Sierra's record order; descriptors after a terminator not read; non-ISO data refused;
  nesting through the unwrapper.
- `IsoTests.Test_disc_reads_as_OS_9_listed_it` reads a test disc (`iso_tests.iso`, under `CLASSICMAC_CORPUS`, not in
  the repository) with the listing Mac OS 9.0 made of it in SheepShaver beside it, and requires no diagnostics and the
  same names, order, types, creators, flags, icon positions, dates and fork sizes for every entry. Every [Verified]
  rule in this document was checked on that disc.
- `tests/ClassicMac.Files.Tests/RawCdTests.cs` covers the raw and cue-sheet paths of §2.1.

## 8. Not covered

- Joliet and Rock Ridge, which the Mac does not read on an ISO disc (§2.2, §2.9); UDF, a separate file system.
- El Torito boot images, Photo CD image packs and Video CD tracks: the ISO files are read, nothing more.
- Other raw formats (2340-byte sectors, 2448-byte sectors with subchannel data) and the CloneCD, Alcohol, Nero and
  DiscJuggler image formats; audio tracks.
- Writing ISO 9660, High Sierra or CD images.
- Open: whether the plug-in reads a record that starts exactly at a directory's `end` (ClassicMac does not, §5); what
  the Mac's arithmetic does with a High Sierra date past 6 February 2040, 06:28:15 (presumably wraps; not traced).
