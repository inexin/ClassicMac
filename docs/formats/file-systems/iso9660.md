# ISO 9660, High Sierra and CD images — an implementer's specification

This document describes CD-ROM volumes in the ISO 9660 and High Sierra formats as Mac OS 9 reads them, together with
the containers CD images travel in: raw-sector `.bin` files and the cue sheets that describe them. It is complete
enough to write a reader that lists the same files, with the same names, types, creators, Finder flags, dates and
forks, as a Mac running Mac OS 9.0 shows for the same disc. It is the behaviour of `ClassicMac.Files.Iso`
(`IsoReader`, `RawCdReader`, `CueSheetReader`), written so that the code never has to be read.

The on-disc layout is the standard's. Everything the Mac adds or decides for itself — which descriptor it uses, how it
turns identifiers into Mac names, where type and creator come from, which record is the resource fork, how dates and
damaged directories are handled — comes from Apple's two file-system plug-ins for Foreign File Access, **ISO 9660
File Access** and **High Sierra File Access** (version 5.3, as shipped with Mac OS 9.0). Both are built from one
source; where they differ, this document says so.

References:

- **ECMA-119** (= ISO 9660): volume and file structure of CD-ROM. The layout of descriptors, path tables and directory
  records.
- **The High Sierra proposal** (the High Sierra Group's working paper, 1986), from which ISO 9660 was made. Same ideas,
  different offsets.
- **ECMA-130**: the CD-ROM sector formats (sync, header, modes). The CD-ROM XA and CD-i system descriptions for mode 2
  and the XA/CD-i directory extensions.
- **Apple's ISO 9660 extensions**: the `AA` system-use entry that carries a Macintosh file type, creator and Finder
  flags, and the use of associated files for resource forks.
- **Mac OS 9.0**: the disassembly of ISO 9660 File Access and High Sierra File Access 5.3 (68k code), and of Apple
  CD/DVD Driver 1.3.1 (the SCSI and ATAPI CD drivers) for what reaches the file system; checked on a test disc in
  SheepShaver, Mac OS 9.0, where every entry the Mac listed matched.
- **The CDRWIN cue sheet format** (Golden Hawk Technology), the de facto format for `.cue` files.

## 1. Conventions

The shared conventions of [README.md](README.md) apply, with these differences.

- **Both-endian fields.** ISO 9660 and High Sierra store most numbers twice: a little-endian copy followed by a
  big-endian copy of the same value (`u32 both` is 8 bytes, `u16 both` is 4). The tables give the offset of the
  whole pair and note which half the Mac reads. The Mac, a big-endian machine, reads the **big-endian half** of every
  pair, and the big-endian (type M) path table; the one little-endian value it reads is the path table size, only to
  compare it with the big-endian one (§3.2) [Code].
- A **sector** here is **2048 bytes** (a CD-ROM mode 1 user-data block). A **logical block** is the volume's own
  block size (§3.2), 512, 1024 or 2048 bytes; extents and lengths in blocks use it. A **raw sector** is 2352 or 2336
  bytes (§13).
- Offsets in a sector or record are from its first byte, in decimal with hex where useful (`881 ($371)`).
- Identifier text on the disc is shown as raw bytes; the Mac shows those bytes as **Mac OS Roman**, untranslated.
- Source tags are the README's. **[Code]** without a name means ISO 9660 File Access (or High Sierra File Access) 5.3
  from Mac OS 9.0; **[Code: CD driver]** means Apple CD/DVD Driver 1.3.1. **[Verified]** means the test disc was read
  in SheepShaver, Mac OS 9.0 (the image attached as a disk, since SheepShaver serves CDs through its own driver) and
  the Mac's listing matched. **[Author]** for cue sheets means the CDRWIN documentation.
- Statements that start **ClassicMac:** describe ClassicMac's own output and limits, not the format; they carry no
  source tag.

## 2. From image to volume

A CD image reaches the volume readers as a run of 2048-byte blocks, the same thing a CD drive hands the Mac. How it
gets there:

| Input | What is done | Then |
| --- | --- | --- |
| Cooked image (`.iso`, `.toast`, `.cdr`, `.img`): 2048-byte blocks | nothing | volume readers |
| Raw image (`.bin`): 2352- or 2336-byte sectors | user data cut out of each sector (§13) | volume readers |
| Cue sheet (`.cue`) with its `.bin` beside it | data tracks placed at their sectors (§14), cut as above, last session found (§15) | volume readers |

The Mac's CD driver never parses sectors: it asks the drive for 2048-byte blocks and the drive strips sync, header,
subheader and error-correction bytes [Code: CD driver]. So the 2048-byte blocks are all a Mac file system ever sees,
and raw sector bytes cannot change what the Mac shows.

The volume readers are then tried in the Mac's mount order (§12): an Apple partition map, then HFS (the master
directory block at byte 1024), and only if neither is there, ISO 9660 or High Sierra [Code]. File extensions play no
part: every container is recognised by content.

ClassicMac: the reader order is partition map, HFS, MFS, DOS partition table, FAT, raw CD, cue sheet, ISO 9660. A
raw image or a cue sheet comes out as one file (named after the image, without its extension, or `CD`) whose data
fork is the cooked disc, which the same readers then open.

## 3. Volume descriptors

### 3.1 Finding the descriptor

The volume descriptors start at **sector 16** (byte `$8000`), one per 2048-byte sector, and end with a terminator
[Doc]. Sectors 0–15 are the system area, which the ISO reader ignores [Doc].

The plug-in first looks for an **anchor**: the sector 16 sectors after the start of the last session (section 15),
then sector 16 itself. The anchor passes when its identifier is `CD001` or `CD-I ` and its version is 1; its type
byte is not checked. Nothing else is tried: with no anchor the disc is not an ISO volume (−58) [Code].

From the anchor, each sector is examined in turn [Code]:

| Test | Meaning |
| --- | --- |
| byte 0 = 255 and bytes 1–5 = `CD001` | ISO terminator: stop, no volume |
| byte 8 = 255 and bytes 9–13 = `CDROM` | High Sierra terminator: stop, no volume |
| byte 0 = 1, byte 6 = 1, bytes 1–5 = `CD001` | ISO 9660 primary volume descriptor |
| byte 0 = 1, byte 6 = 1, bytes 1–5 = `CD-I ` | CD-i disc's primary descriptor (read as ISO 9660, with the CD-i rules below) |
| byte 8 = 1, byte 14 = 1, bytes 9–13 = `CDROM` | High Sierra standard file structure volume descriptor |
| anything else (boot record, supplementary, partition) | skipped |

- Only the **primary** descriptor is used. A supplementary descriptor (type 2), and so **Joliet**, is never used; the
  plug-in has no Unicode name code at all [Code]. Rock Ridge is not read either (§16).
- The descriptor's version byte must be 1 [Code].
- There is **no fixed limit** on the number of sectors examined: the scan runs until a primary descriptor, a
  terminator (with no primary descriptor: −60) or a read error (−58) [Code].
- ClassicMac: the standard identifiers (terminators' included) are compared without regard to case; the anchor is
  D + 16 then 16 only when the image's sessions are known (a cue sheet, or a raw image whose sector addresses jump;
  section 15), otherwise sector 16; an anchor also passes with High Sierra's `CDROM` at byte 9 and version 1 at
  byte 14; the scan examines at most 64 sectors from the anchor, a limit the Mac does not have.

A disc whose ISO descriptor passes these tests can still be declined by the ISO plug-in [Code]:

- **Photo CD.** The plug-in answers −58, leaving the disc to Kodak's Photo CD Access, when all of these hold: the
  system identifier (offset 8, 17 bytes) is `CD-RTOS CD-BRIDGE`; the descriptor holds `CD-XA001` at byte 1024;
  bytes 64–95 (`$40`–`$5F`) of logical sector 0 read `PPPPHHHHOOOOTTTTOOOO____CCCCDDDD` ("PHOTO_CD" with each
  character four times); and Gestalt `'kpcd'` exists, that is, Photo CD Access is installed. Without it, a Photo CD
  mounts as an ordinary ISO volume.
- **UDF.** When Gestalt `'kudf'` exists, the plug-in examines up to 10 sectors after the primary descriptor (the
  count stops falling once `BEA01` is seen; the search ends at `TEA01` or a read error) and answers −58 if it finds
  `NSR02`, so UDF takes the disc.

ClassicMac reads both as ISO 9660, as a Mac without those extensions does.

| 140 | 4 | u32 LE | Location of the type L (little-endian) path table |

The layout is ECMA-119's [Doc]. The Mac **rejects** the volume when [Code]:

- the file structure version is neither 0 nor 1;
- on an ISO (not CD-i) disc, the little- and big-endian path table sizes differ.

The logical block size must be a power of two from 512 to 2048 [Doc]; ClassicMac rejects any other value. A disc is
an **XA disc** when `CD-XA001` is at byte 1024 [Doc]; this changes only where the Apple extension is looked for
(§9.3) [Code].

High Sierra puts an 8-byte block number in front of the type byte and so moves everything [Doc]:

| Offset | Size | Type | Meaning |
| --- | --- | --- | --- |
| 0 | 8 | u32 both | Logical block number of this descriptor |
| 8 | 1 | u8 | Descriptor type: 1 = standard file structure volume descriptor (**used**) |
| 9 | 5 | chars | Standard identifier `CDROM` (**used**) |
| 14 | 1 | u8 | Descriptor version, 1 (**used**) |
| 15 | 1 | — | Unused |
| 16 | 32 | chars | System identifier |
| 48 | 32 | chars | Volume identifier |
| 80 | 8 | — | Unused |
| 88 | 8 | u32 both | Volume space size |
| 96 | 32 | — | Unused |
| 128 | 4 | u16 both | Volume set size |
| 132 | 4 | u16 both | Volume sequence number |
| 136 | 4 | u16 both | Logical block size; big-endian half at 138 (**used**) |
| 140 | 8 | u32 both | Path table size |
| 148 | 16 | 4 × u32 LE | Type L path table and three optional copies |

High Sierra has no file structure version check and no path table size comparison [Code]. Its terminator is type 255
at byte 8 with `CDROM` [Doc].

### 3.4 Other descriptors

| Type | Name | Mac OS 9 |
| --- | --- | --- |
| 0 | Boot record (El Torito) | ignored [Code] |
| 2 | Supplementary (Joliet when its escape sequences say UCS-2) | ignored [Code] |

## 4. The path table

The path table lists every directory with its extent. The Mac uses it for one thing: **the root directory is the
first entry of the big-endian (type M) path table** [Code]. The root directory record inside the descriptor is not
used [Code]. Nothing else in the path table is read; every other directory is found through directory records.

ISO 9660 path table record [Doc]:

| Offset | Size | Type | Meaning |
| --- | --- | --- | --- |
| 0 | 1 | u8 | Length of the directory identifier |
| 1 | 1 | u8 | Extended attribute record length, in logical blocks |
| 2 | 4 | u32 | Extent location, in logical blocks (big-endian in a type M table) (**used**) |
| 6 | 2 | u16 | Parent directory number |
| 8 | n | chars | Directory identifier (the root's is one zero byte), padded to even length |

High Sierra path table record [Doc]:

| Offset | Size | Type | Meaning |
| --- | --- | --- | --- |
| 0 | 4 | u32 | Extent location, in logical blocks (big-endian in a type M table) (**used**) |
| 4 | 1 | u8 | Extended attribute record length |
| 5 | 1 | u8 | Length of the directory identifier |
| 6 | 2 | u16 | Parent directory number |
| 8 | n | chars | Directory identifier, padded to even length |

The path table's byte offset is (location × logical block size); the root's byte offset is (extent × logical block
size). ClassicMac rejects the volume when either lies outside the image, or the root extent is 0.

## 5. Directory records

A directory is a run of variable-length records packed into sectors. A record never crosses a 2048-byte sector
boundary; the rest of a sector after its last record is zero [Doc].

ISO 9660 directory record [Doc]:

| Offset | Size | Type | Meaning |
| --- | --- | --- | --- |
| 0 | 1 | u8 | Record length in bytes (even; 0 = none here) |
| 1 | 1 | u8 | Extended attribute record length, in logical blocks |
| 2 | 8 | u32 both | Extent location, in logical blocks; big-endian half at 6 (**used**) |
| 10 | 8 | u32 both | Data length in bytes; big-endian half at 14 (**used**) |
| 18 | 7 | date | Recording date and time (§10) |
| 25 | 1 | u8 | File flags (below) |
| 26 | 1 | u8 | File unit size, in logical blocks (0 = not interleaved) |
| 27 | 1 | u8 | Interleave gap size, in logical blocks |
| 28 | 4 | u16 both | Volume sequence number |
| 32 | 1 | u8 | Length of the file identifier (n) |
| 33 | n | chars | File identifier |
| 33 + n | 0 or 1 | — | Pad byte, present when n is even |
| … | to end | bytes | System use (§9) |

High Sierra directory record [Doc]:

| Offset | Size | Type | Meaning |
| --- | --- | --- | --- |
| 0 | 1 | u8 | Record length |
| 1 | 1 | u8 | Extended attribute record length |
| 2 | 8 | u32 both | Extent location |
| 10 | 8 | u32 both | Data length |
| 18 | 6 | date | Recording date and time: year − 1900, month, day, hour, minute, second (no time zone) |
| 24 | 1 | u8 | File flags |
| 25 | 1 | — | Reserved |
| 26 | 1 | u8 | Interleave size |
| 27 | 1 | u8 | Interleave skip factor |
| 28 | 4 | u16 both | Volume sequence number |
| 32 | 1 | u8 | Length of the file identifier |
| 33 | n | chars | File identifier, then a pad byte when n is even, then system use |

File flags [Doc]:

| Bit | Mask | Meaning | Mac OS 9 |
| --- | --- | --- | --- |
| 0 | `$01` | Existence: hidden from the user | invisible (§9.5) [Code][Verified] |
| 1 | `$02` | Directory | folder (not on CD-i discs, §5.2) [Code] |
| 2 | `$04` | Associated file | resource fork (§8.1) [Code][Verified] |
| 3 | `$08` | Record format in the extended attributes | ignored [Code] |
| 4 | `$10` | Permissions in the extended attributes | ignored [Code] |
| 5–6 | `$60` | Reserved | ignored |
| 7 | `$80` | Multi-extent: not the file's last extent | ignored: each extent is its own entry (§8.3) [Verified] |

### 5.1 What the Mac reads of a record

The plug-ins copy a fixed amount of each record into a buffer: **268 ($10C) bytes** for ISO 9660, **82 ($52)** for
High Sierra [Code]. Bytes past the end of the image read as zeros. Two consequences:

- An ISO record is at most 255 bytes, so the buffer holds all of it and some of what follows; a system-use entry that
  starts inside the record is read in full even when it runs past the record's length (§9.3) [Code].
- A High Sierra record is seen only as far as byte 81. System-use bytes beyond it read as zeros [Code].

### 5.2 CD-i discs

A disc whose descriptor says `CD-I ` keeps a directory's "is a folder" bit in its system-use field, not in the flags:
the system use starts with a 4-byte owner ID and a 2-byte attributes word, and bit 15 of the attributes (byte 4 of
the system use, mask `$80`) marks a directory [Doc]. The Mac reads the folder bit there on CD-i discs and ignores flag
bit 1 [Code]. The hidden and associated bits still come from the flags.

## 6. Reading a directory

### 6.1 Where a listing starts and ends

A directory is reached through a record for it (for the root, the first record at the path table's extent, which is
the root's own `.` record). Its listing [Code]:

1. `start` = (the record's extent + its extended attribute length) × logical block size.
2. The first record at `start` is `.` (the directory itself); its data length gives the directory's size, so
   `end` = `start` + that length.
3. The second record is `..` (the parent).
4. Entries are read from after `..` while the position is not past `end`.

`.` and `..` are recognised by position, not by their identifiers (one byte, 0 and 1) [Code].

ClassicMac: the record at exactly `end` is still tried (the test is "position greater than end"), and folders are
read depth first in listing order, their files placed where the folder's record appears.

### 6.2 Valid records

A record is **valid** when all of these hold [Code][Verified]:

| Test | Failing it means |
| --- | --- |
| record length ≠ 0 | the unused tail of a sector |
| extent (big-endian, read as signed) > 0 | a record with extent 0, which some discs use for an empty file |
| 1 ≤ identifier length ≤ 37 | a damaged record, or a long name from a non-conforming mastering program |
| High Sierra only: year byte ≤ 140 (year ≤ 2040) | — |

An invalid record is handled like the zero tail of a sector [Code][Verified]:

1. Move to the next 2048-byte sector boundary (of the image, whatever the logical block size). If the position is
   already on a boundary, it stays there.
2. If that is at or past `end`, the listing ends.
3. If the record there is invalid too, the listing ends.
4. Otherwise it is the next entry.

So an invalid record in the middle of a sector **hides the rest of that sector**, and an invalid record at the start
of a sector **ends the whole directory** [Verified]. A 38-byte identifier or an empty file stored with extent 0
therefore makes files disappear from the Mac's listing; ClassicMac lists exactly what the Mac lists and nothing more.

### 6.3 Entries

Each entry is one file or one folder. A folder is a record with the directory bit (§5, §5.2). A file is one record,
or two records paired as data and resource fork (§8.1). Entries are numbered from 1 in listing order within their
directory, folders included; the number places the Finder icon (§9.6) [Code][Verified].

ClassicMac: a folder whose data (by byte offset) has already been read is skipped with `iso.folder-loop`; reading
stops after `MaxVolumeEntries` entries (default 1,000,000) with `iso.too-many-entries` (§18).

## 7. Names

### 7.1 From identifier to Mac name

ISO 9660 file identifiers have the form `NAME.EXT;1`, the number after `;` being the file version [Doc]; directory
identifiers have no version. The Mac converts an identifier to a name in this order [Code][Verified]:

1. **Cut to 31 bytes** (the longest Mac file name) — before anything else, so a long name loses its version or part
   of it first.
2. **Trim trailing spaces.**
3. **Strip the version:** if the name ends in `;` followed by nothing but digits (possibly none), remove the `;` and
   the digits.
4. **Drop a final `.`**, but only when the name is **9 bytes or shorter** at this point.

Nothing else changes [Code][Verified]:

- the bytes are shown as Mac OS Roman, with no character set conversion;
- case is kept (`mixed.Case;1` stays `mixed.Case`);
- `:` is not filtered, though it is the Mac's path separator;
- there is no 8.3 check and no mapping of `_` or other characters.

Examples [Verified]:

| Identifier | Bytes | Mac name |
| --- | --- | --- |
| `README.TXT;1` | 12 | `README.TXT` |
| `NOEXT.;1` | 8 | `NOEXT` |
| `LONGNAME12.;1` | 13 | `LONGNAME12.` (the dot is kept: 11 bytes after the version goes) |
| a 30-byte name + `;1` | 32 | the 30-byte name (the cut leaves `…;`, and the empty version goes) |
| a 33-byte name + `;1` | 35 | its first 31 bytes |

High Sierra names follow the same rules [Code].

### 7.2 Holding Option at mount

If Option is held when the disc mounts, steps 3 and 4 are skipped for the whole volume: names keep `;1` and their
final dot [Code]. The 31-byte cut, the space trim, case and character handling do not change [Code]. Lookups then
need the raw name, and a resource fork pairs with its data fork only when the names, versions included, match (§8.1)
[Code].

ClassicMac: always reads as the Mac does without Option.

### 7.3 Duplicates

Two records that convert to the same name are both listed [Code]. The Mac looks names up without regard to case and
finds the first [Code]. Multi-extent files (§8.3) and a data fork before its resource fork (§8.1) both produce such
duplicates [Verified].

## 8. Files, forks and extents

### 8.1 Associated files are resource forks

An **associated file** (flag bit 2) holds the **resource fork** of the file with the same name [Code][Verified]. The
two records must be **adjacent**, in this order:

| Format | First record | Second record |
| --- | --- | --- |
| ISO 9660 | the associated one (resource fork) | the file (data fork) |
| High Sierra | the file (data fork) | the associated one (resource fork) |

Pairing rules [Code][Verified]:

- ISO: an associated record takes the **immediately following** record as its data fork when that record is valid,
  is not associated itself, and has the same converted name (§7.1). The pair is one entry.
- High Sierra: a record takes the immediately following record as its resource fork when that record is valid,
  associated, and has the same converted name.
- An associated record with no partner is a file with an **empty data fork** and that resource fork [Verified].
- Records in the wrong order for the format are **two entries with the same name**, one with only a data fork and
  one with only a resource fork [Verified].
- "The same name" is decided by `_RelString`, **case-insensitive and diacritical-sensitive**, on the converted names
  (at most 31 bytes, `;n` stripped) [Code]: `readme.txt` pairs with `README.TXT`, `CAFE` does not pair with `CAFÉ`,
  `A;1` pairs with `A;2`, and two names that differ only after byte 31 pair. This is the order and case folding the
  File Manager uses for HFS names, quirks included (`á` and `Á` differ, `$CA` equals a space); see
  [HFS-MFS.md](HFS-MFS.md) section 6.6.
  With Option held the names keep their versions (§7.2), so `A;1` and `A;2` no longer pair.
- ClassicMac compares the converted names without regard to case, as Mac OS Roman read into Unicode with ordinal
  case folding, not with Apple's tables. The two agree on A–Z and on the accented letters `_RelString` folds; they
  differ where its tables do not fold (`á`/`Á` and `ÿ`/`Ÿ` pair in ClassicMac, not on the Mac) or equate other
  characters (`$CA` and a space pair on the Mac, not in ClassicMac).
- ClassicMac: on ISO, a second associated record after an associated one is consumed by the pair but gives no fork.
  The Mac does not pair them: the second associated record starts an entry of its own [Code].

### 8.2 Where a fork's bytes are

A fork's bytes start at (extent + extended attribute record length) × logical block size and run for the data length
[Doc][Verified]. The extended attribute record's contents (owner, permissions, record format, dates) are ignored;
only its length moves the data [Verified].

An **interleaved** fork (file unit size ≠ 0) is stored as units of `unit` logical blocks separated by gaps of `gap`
logical blocks, starting with a unit [Doc]; the Mac reads it [Verified]:

```
offset = (extent + xar) × blockSize
repeat until length bytes are read:
    read min(unit × blockSize, remaining) bytes at offset
    offset += (unit + gap) × blockSize
```

ClassicMac: a fork that runs past the end of the image is cut at the image's end and reported (`iso.short`).

### 8.3 Multi-extent files

ECMA-119 lets a file span several records with the same identifier, all but the last having flag bit 7 [Doc]. The
Mac does **not** join them: each extent is listed as a separate file of the same name [Verified]. ClassicMac lists
them the same way.

### 8.4 Access

The volume is read-only and locked; writes fail with `wPrErr` (−44) [Code].

## 9. Finder information

### 9.1 Defaults

A file with no Apple extension is type `'TEXT'`, creator `'hscd'`, Finder flags `$0100` (hasBeenInited)
[Code][Verified]. There is **no mapping from name extensions** to types [Code]: `.GIF`, `.SIT` and `.JPG` files are
all `'TEXT'`/`'hscd'` on the Mac.

### 9.2 The system-use field

The system-use field starts at record offset 33 + n, plus one pad byte when n (the identifier length) is even, and
runs to the record length [Doc]. The Mac looks at it only when 33 + n is less than the record length [Code]. Folders
get no system-use processing [Code].

Two forms of Apple's extension exist. The Mac looks for the old one first.

### 9.3 `BA`: the old form

When the system-use field **starts** with `BA` [Code]:

| Offset | Size | Type | Meaning |
| --- | --- | --- | --- |
| 0 | 2 | chars | `BA` |
| 2 | 1 | u8 | Kind |
| 3 | 4 | OSType | File type |
| 7 | 4 | OSType | Creator |
| 11 | 2 | u16 | Finder flags (used by kind 6 only) |

| Kind | Type and creator | Finder flags |
| --- | --- | --- |
| 2 or 4 | from the entry | OR `$0100` |
| 3 or 5 | from the entry | OR `$2100` (hasBundle, hasBeenInited) |
| 6 | from the entry | OR ((stored flags AND `$B020`) OR `$0100`) |
| anything else | `'TEXT'`/`'hscd'` | OR `$0100`; no `AA` search follows |

The kinds and their flag rules are from the disassembly [Code]; kinds 3 and 6 were checked on the test disc
[Verified]. `BA` is recognised only as the first two bytes of the system-use field, and the XA skip of §9.4 does not
apply to it [Code]. What the kinds mean is not in the code; likely, 1 is ProDOS (ignored here), 2 and 3 HFS type and
creator without and with a bundle, 4 and 5 the same in a form that also carries an icon (ignored), and 6 HFS with
explicit Finder flags.

### 9.4 `AA`: Apple's extension

Otherwise, the field is scanned for `AA` entries [Code]:

| Offset | Size | Type | Meaning |
| --- | --- | --- | --- |
| 0 | 2 | chars | Signature `AA` [Doc] |
| 2 | 1 | u8 | Entry length, 14 for the HFS form [Doc] |
| 3 | 1 | u8 | System-use ID: 1 = ProDOS, 2 = HFS [Doc] |
| 4 | 4 | OSType | File type (HFS form) [Doc] |
| 8 | 4 | OSType | Creator (HFS form) [Doc] |
| 12 | 2 | u16 | Finder flags (HFS form) [Doc] |

The scan [Code]:

1. `p` = the start of the system-use field; on an XA disc (§3.2), `p` += 14, skipping the XA system-use entry.
2. While `p` + 14 fits in the record buffer (§5.1) and `p` is inside the record:
   - if bytes `p`…`p+1` are `AA` and byte `p+3` is 2, this is the entry: stop;
   - else if the length byte at `p+2` is below 4, stop with no entry;
   - else `p` += the length byte.
3. No entry: the defaults of §9.1.

An `AA` entry of ID 2 gives the type, the creator, and Finder flags **set** (not ORed) to (stored flags AND `$B020`)
OR `$0100` [Code][Verified]. The mask keeps only isAlias (`$8000`), hasBundle (`$2000`), nameLocked (`$1000`) and
bit 5 (`$0020`) [Code]. It removes, among others, **isInvisible** (`$4000`), **isStationery** (`$0800`) and
**hasCustomIcon** (`$0400`), so an `AA` entry can never make a file invisible, stationery or custom-iconned
[Code][Verified]: stored flags `$6500` read as `$2100`.

- The ProDOS form (ID 1) is skipped [Verified].
- SUSP conventions are not honoured: no `SP` entry skip, no `CE` continuation areas [Code]. An `AA` entry in a
  continuation area is never found.

### 9.5 Combining the two records, and hidden files

A file's Finder information is built from its data record, then from its resource record, starting from type
`'TEXT'`, creator `'hscd'` and flags 0 [Code]:

1. For each record present (data first, then resource): take its type and creator from §9.3, §9.4 or §9.1 (replacing
   what was there), apply its flag rule, and if the record's hidden flag (bit 0) is set, OR in isInvisible (`$4000`).
2. So the **associated (resource) record wins**: if it has no extension, the file is `'TEXT'`/`'hscd'` even when the
   data record has an `AA` entry [Code][Verified].

The hidden flag is the only way a file becomes invisible on the Mac [Code][Verified]. It hides folders too [Code].

Flags left by the data record survive when the resource record's rule ORs (default or `BA`) and are replaced when it
has an `AA` entry; this follows from applying the rules in order and is [Fitted?].

### 9.6 Icon positions

Files listed by index (as the Finder lists a folder) get an icon position on a six-column grid of 64-pixel cells, in
entry order (§6.3) [Code][Verified]:

```
v = ((i − 1) div 6) × 64
h = ((i − 1) mod 6) × 64
```

with `i` the entry number from 1. The same formula with index 0 is used when a file is looked up by name, giving
h = −64, v = 0 [Code][Verified]. ClassicMac reports the listed position. The extended Finder information is all zero
[Code].

## 10. Dates

ISO 9660 dates in directory records are 7 bytes [Doc]:

| Offset | Size | Type | Meaning |
| --- | --- | --- | --- |
| 0 | 1 | u8 | Year − 1900 |
| 1 | 1 | u8 | Month, 1–12 |
| 2 | 1 | u8 | Day, 1–31 |
| 3 | 1 | u8 | Hour, 0–23 |
| 4 | 1 | u8 | Minute, 0–59 |
| 5 | 1 | u8 | Second, 0–59 |
| 6 | 1 | i8 | Offset from GMT in 15-minute steps |

High Sierra has the first six bytes only [Doc].

The Mac's conversion [Code][Verified]:

- The date is taken as **local wall-clock time**; the **GMT offset is ignored** (12:00 at +9 hours and at −5 hours
  both read as 12:00) [Verified].
- ISO: a year of **2040 or later** reads as **6 February 2040, 00:00:00** [Code][Verified].
- A year before 1904 reads as **1904**, month, day and time kept [Code][Verified].
- A month outside 1–12 reads as 1; a day outside 1–31 reads as 1 [Code][Verified].
- Hours, minutes and seconds are not checked. The fields then go to `Date2Secs`, which is plain arithmetic with no
  range checks, so a value past its range carries into the next unit: 31 February reads as 3 March (2 March in a leap
  year), and 25:61:61 as 02:02:01 the next day. Its leap-year rule is "year divisible by 4", right for 1904–2040
  [Code].
- High Sierra: a record with a year byte over 140 is invalid (§6.2) [Code].
- A file's creation, modification and backup dates are all the date of its **associated (resource) record** when it
  has one, else of its data record [Code][Verified].

ClassicMac computes dates the same way: a day past the end of its month rolls into the next month, and hours,
minutes and seconds are added without range checks. Only a High Sierra date late in 2040 can pass the last Mac date
(6 February 2040, 06:28:15); ClassicMac reads it as that date, where the Mac's unchecked arithmetic would
presumably wrap. That case was not traced.

## 11. What the Mac shows that ClassicMac does not report

ClassicMac reports each file's name, folder path, type, creator, Finder flags, icon position, creation and
modification dates (the same value) and both forks. The Mac also shows the following, which ClassicMac does not
report:

- **Volume name**: the first 27 bytes of the volume identifier, trailing spaces trimmed, converted as in §7.1; an
  empty identifier gives `Untitled` [Code][Verified]. With Option held, the name keeps `;n` and its dot [Code].
- **Volume dates**: parsed from the descriptor's 17-byte text dates (§3.2), GMT offset ignored [Code].
- **Folders**: Finder flags `$0100`, view `$0100`, scroll position (−8, −16); the hidden flag makes a folder
  invisible [Code]. ClassicMac produces no folder entries, only folder paths, so folder dates, flags and
  invisibility are lost.
- **File and folder IDs**: the byte offset of the entry's (first) directory record on the disc; the root's ID is 2
  [Code][Verified].
- **Locked volume** (§8.4).

## 12. Hybrid discs

A **hybrid** disc carries an HFS volume and an ISO 9660 volume over the same data: typically an Apple partition map
in the system area, an HFS partition, and an ISO descriptor at sector 16. On the Mac [Code: CD driver][Code]:

- The CD driver looks at block 0: if it holds a driver descriptor (`ER`) or zeros, it scans for partition entries
  (`PM`) at a 512-byte stride, then at a 2048-byte stride. Each `Apple_HFS` partition becomes a drive of its own, and
  no whole-disc drive is made, so the ISO volume is never offered to the file systems.
- Without a partition map, the whole disc is one drive. Mounting always tries HFS first (the master directory block at
  byte 1024); only when that fails do Foreign File Access and the ISO plug-in get the disc.

So **a hybrid disc mounts as HFS**, and its ISO side is never seen on a Mac; both cannot be mounted from one disc.
ClassicMac does the same by trying the partition map and HFS readers before the ISO reader (§2). The HFS side is
specified in [HFS-MFS.md](HFS-MFS.md).

ClassicMac's partition map reader reads the map as the CD driver does (block 0 with `ER` or zeros, entries at a
512-byte stride, else a 2048-byte one), so these hybrids read as HFS too. Its remaining differences from the driver
are listed in [HFS-MFS.md](HFS-MFS.md) section 3.4.

## 13. Raw CD images

### 13.1 Sector formats

A raw image stores every sector as the disc carries it, 2352 bytes, or 2336 bytes without the sync and header
[Doc]:

2352-byte sector, mode 1 [Doc]:

| Offset | Size | Meaning |
| --- | --- | --- |
| 0 | 12 | Sync: `00`, ten `FF`, `00` |
| 12 | 3 | Address: minute, second, frame (BCD) |
| 15 | 1 | Mode: 1 |
| 16 | 2048 | **User data** |
| 2064 | 4 | EDC |
| 2068 | 8 | Reserved (zero) |
| 2076 | 276 | ECC (P and Q parity) |

2352-byte sector, mode 2 (CD-ROM XA) [Doc]:

| Offset | Size | Meaning |
| --- | --- | --- |
| 0 | 12 | Sync |
| 12 | 3 | Address |
| 15 | 1 | Mode: 2 |
| 16 | 4 | Subheader: file number, channel number, submode, coding information |
| 20 | 4 | Copy of the subheader |
| 24 | 2048 | **User data** (form 1), followed by EDC and ECC |
| 24 | 2324 | User data (form 2), followed by a 4-byte EDC |

Submode bit 5 (`$20`) marks form 2 [Doc]. A 2336-byte sector is a mode 2 sector from byte 16: subheader at 0, copy at
4, user data at **8** [Doc].

| Sector | User data at | 2048-byte block |
| --- | --- | --- |
| 2352, mode 1 | 16 | yes |
| 2352, mode 2 form 1 (subheader byte 18 bit 5 clear) | 24 | yes |
| 2352, mode 2 form 2 | — | none: reads as 2048 zeros |
| 2352, mode 0 or any other mode byte | — | none: reads as zeros |
| 2336, form 1 (byte 2 bit 5 clear) | 8 | yes |
| 2336, form 2 | — | none: reads as zeros |

A drive returns only form 1 and mode 1 data to a 2048-byte read, so form 2 data never reaches a Mac file system
[Code: CD driver]. ClassicMac: each sector's own mode and submode decide, so a disc may mix modes; EDC and ECC
are not checked, and the image's first sector is logical block 0, except where the addresses show a gap between
sessions (§15).

### 13.2 Recognising a raw image

ClassicMac recognises a raw image by content (the Mac has no raw images to recognise):

- **2352-byte sectors**: the length is a multiple of 2352 and at least 17 sectors, and sector 16 or sector 0 starts
  with the sync pattern and has mode byte 1 or 2.
- **2336-byte sectors** (no sync to test): the length is a multiple of 2336 and at least 17 sectors, the two
  subheader copies of sector 16 are equal, and the cooked data holds a volume: `CD001` at byte 1 or `CDROM` at byte 9
  of block 16, or `ER` at byte 0 (partition map) or `BD` at byte 1024 (HFS) of the disc.

The cooked disc is (number of sectors × 2048) bytes, handed to the volume readers (§2).

## 14. Cue sheets

A cue sheet is a text file that lists a disc's tracks and the image files that hold them [Author]. Only the commands
below matter here; every other line (`REM`, `CATALOG`, `PERFORMER`, `TITLE`, `PREGAP`, `POSTGAP`, `FLAGS`, `ISRC`, …)
is ignored.

| Command | Form | Meaning |
| --- | --- | --- |
| `FILE` | `FILE "name" type` or `FILE name type` | The image file that holds the following tracks [Author] |
| `TRACK` | `TRACK nn mode` | A track and its data mode [Author] |
| `INDEX` | `INDEX nn mm:ss:ff` | An index point, as a time in the current file: minutes, seconds, frames (75 per second) [Author] |

Track modes and their sector sizes [Author]:

| Mode | Bytes per sector | Read by ClassicMac |
| --- | --- | --- |
| `AUDIO` | 2352 | skipped |
| `MODE1/2048` | 2048 | as is |
| `MODE1/2352` | 2352 | cooked (§13) |
| `MODE2/2336` | 2336 | cooked (§13) |
| `MODE2/2352` | 2352 | cooked (§13) |
| `MODE2/2048` | 2048 | as is (not a CDRWIN mode, but written by some programs) |
| `CDG`, `CDI/2336`, `CDI/2352`, others | — | not read (`container.unreadable`) |

ClassicMac's reading:

- **Text**: at most 64 KiB, no zero bytes, read as Latin-1 with a UTF-8 byte order mark removed; lines end in CR, LF
  or both; commands are matched without regard to case and leading spaces. A file is a cue sheet when it has at least
  one `FILE` line and one `TRACK` line.
- **Tracks**: a `TRACK` line becomes a track at its `INDEX 01` (`INDEX 1` is accepted), in the file named by the last
  `FILE` line. `INDEX 00` (the pregap) is ignored. A track with no `INDEX 01` is dropped. The `FILE` type (`BINARY`,
  `MOTOROLA`, `WAVE`, …) is not checked.
- **Sessions**: `REM SESSION nn` (a comment in CDRWIN, written by other programs for multisession discs) puts the
  tracks after it in session nn; without it every track is in session 1.
- **Files**: found among the files beside the cue sheet by name, without regard to case. A path in the name is not
  followed.
- **Placing tracks**: the files are laid end to end in the order the sheet names them. In a file, a track's sectors
  start at its `INDEX 00` (the pregap) or, without one, its `INDEX 01`, and each sector has its own track's size, so
  a track's bytes start at (the sectors of the tracks before it in the file × their sizes) plus (its INDEX 01 − its
  region start) × its size. A track runs to the next track's region in the same file, or the file's end, rounded
  down to whole sectors. Its absolute sector is the sectors of the files before it plus its INDEX 01, counted from
  track 1's.
- **The gap between sessions**: images often leave out the sectors between sessions (lead-out, lead-in). A raw 2352-byte data track whose first sector's header (§13.1) gives a later address than
  its place in the files is put at the header's address, and the tracks after it move with it. A 2048-byte track has
  no header: its place in the files is taken as its address.
- **The disc**: one file, named after the cue sheet without its extension, whose data fork is the disc's 2048-byte
  blocks numbered by absolute sector, from the first track's: each data track's blocks (§13 for raw sectors) at its
  sector, and zeros for audio tracks, gaps and tracks not read (§2). The last session's start goes with it (§15).
- **Errors**: with no data track the sheet gives nothing (`cue.audio-only`). The track the descriptors come from (the
  last session's first data track, or the first data track when that session has none) must be readable: an
  unreadable mode, a missing file or a track starting past its file's end makes the sheet unreadable. Any other data
  track that cannot be read reads as zeros (`cue.track-unread`).

## 15. Multisession discs

A multisession disc (a CD-R written in several sessions, a CD Extra/Enhanced CD with audio first and data after) has
a volume descriptor set in each data session; the last one describes the whole disc, and its extents are absolute
sector numbers [Doc].

The Mac [Code: CD driver][Code]:

- The driver reports the sessions (its table of contents call, session form): first and last session, and the start
  of the last session's first track. If the drive refuses the call, the driver answers "one session, starting at
  00:02:00", which gives offset 0.
- The plug-in computes D = (start of the last session − start of track 1) and reads the descriptors at sector D + 16
  first, then at sector 16.
- The driver checks each session for a descriptor at its start + 16 sectors. When the last session's root extent is
  at or after that session's start, it maps the whole disc from offset 0, so absolute sector numbers work.

The disc an image gives has no table of contents, so ClassicMac finds the last session itself, then follows the Mac:

- **Cue sheet**: the last session's first track is the first track after the last `REM SESSION` line or, in a sheet
  without those lines, the **last data track** (ClassicMac's reading: a CD Extra's data track, or each later
  session's track, comes after the first session's). D = its absolute sector − track 1's (§14), and the disc is
  mapped from track 1's start.
- **Raw image** (§13) with no cue sheet: a 2352-byte image's sector headers give each sector's address. When the
  address less the sector's index grows somewhere in the image (the image left out the gap between sessions), each
  run of sectors with one offset is placed at its address, and the last run is the last session. Its first track is
  taken to start at the run's first sector or, when that has no descriptor 16 sectors on, 150 sectors later (a
  pregap); this is ClassicMac's rule, not the Mac's. An image whose addresses do not jump (one session, or the gap
  kept), a 2336-byte image (no headers) and a cooked image are read from sector 16 only, by their first session's
  descriptors.
- **Descriptors**: at D + 16 first; when that sector is not an anchor (§3.1), at 16. When the last session's
  primary descriptor's root directory record (byte 156, High Sierra 180) gives an extent at or after the session's
  start, block numbers are absolute; otherwise they count from the session's start.
- **HFS**: a partition map (`ER` or zeros at block D, `PM` at byte 512 or 2048 of it) or an HFS volume (`BD` at
  byte 1024) at the start of a cue sheet's last session is read from that session's start: the CD driver applies the
  session base to the partition map ([HFS-MFS.md](HFS-MFS.md) section 3.4). For a bare HFS volume this is ClassicMac's
  choice; the driver's handling of one was not traced. A raw image's later session is not checked for HFS.

## 16. Where Mac OS 9 differs from ECMA-119

| Standard | Mac OS 9 |
| --- | --- |
| Supplementary descriptors (Joliet) give long Unicode names | ignored; only the primary descriptor (§3) [Code] |
| Rock Ridge (SUSP) entries give POSIX names and attributes | ignored; `SP` and `CE` not honoured (§9.4) [Code] |
| The root is the descriptor's root directory record | the first entry of the big-endian path table (§4) [Code] |
| Both byte orders are equivalent | the big-endian half is read (§1) [Code] |
| Identifiers up to 207 bytes (level 3), versions 1–32767 | 31 bytes kept, cut before the version goes; over 37 bytes the record is invalid (§6.2, §7) [Code][Verified] |
| A zero-length file may have any extent | a record with extent 0 is invalid and hides what follows (§6.2) [Verified] |
| A file may span several extents (flag bit 7) | each extent is a separate file (§8.3) [Verified] |
| Associated files have no fixed meaning | the associated file is the resource fork (§8.1) [Code][Verified] |
| Recording dates carry a GMT offset | the offset is ignored; dates are local (§10) [Verified] |
| Extended attribute records hold owner, permissions and dates | only their length is used (§8.2) [Verified] |
| File flag bit 0 hides a file from the user | the only source of isInvisible (§9.5) [Code][Verified] |
| Name characters are d-characters (A–Z, 0–9, `_`) | any byte is shown as Mac OS Roman, case kept (§7.1) [Code][Verified] |
| Descriptors from sector 16 | on a multisession disc, the last session's first (§15) [Code]; ClassicMac finds the last session from a cue sheet or a raw image's sector addresses |

## 17. Not covered

- **Joliet, Rock Ridge, UDF**: the Mac does not read the first two on an ISO disc (§3.1, §9.4); UDF is a separate
  file system.
- **El Torito boot images**, **Photo CD** image packs and **Video CD** tracks: the ISO files are read, nothing more.
- **Other raw formats**: 2340-byte sectors, 2448-byte sectors with subchannel data, and the CloneCD, Alcohol, Nero
  and DiscJuggler image formats.
- **Audio tracks**: never read.
- **Writing**: ClassicMac does not write ISO 9660, High Sierra or CD images.

## 18. Diagnostics

| Code | Severity | Meaning | What the Mac does |
| --- | --- | --- | --- |
| `iso.too-many-entries` | Error | More than `MaxVolumeEntries` (default 1,000,000) files and folders; reading stopped. | No such limit; a guard against damaged volumes. |
